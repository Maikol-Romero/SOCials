🔍 ¿Qué es Trivy Security?

Trivy Security es un dashboard de seguridad para tu SOC (Security Operations Center). Escanea automáticamente todas las imágenes Docker y paquetes del sistema operativo de las máquinas de tu fleet, buscando vulnerabilidades de seguridad conocidas (CVEs).

No solo detecta vulnerabilidades — las explica con inteligencia artificial, identifica dependencias reales, detecta conflictos de actualización, y marca las que están expuestas a internet para que sepas exactamente qué arreglar primero y cómo.

⚙️ Cómo funciona el pipeline

Cada domingo a la 1:00 AM se ejecuta automáticamente el escaneo completo. El pipeline tiene 6 fases:

1. Escaneo Trivy
→
2. Generación JSON
→
3. IA carry-over
→
4. Enrich con IA
→
5. Dependencias
→
6. Dashboard
Detalle de cada fase

1. Escaneo Trivy — Conecta por SSH a cada máquina, lista todos los contenedores Docker, y ejecuta trivy image en cada uno. También escanea paquetes del sistema operativo host.

2. Generación JSON — Consolida todos los resultados en latest.json, deduplica por CVE+paquete, detecta qué máquinas e imágenes tienen cada vulnerabilidad, y genera la resolución de las que desaparecieron.

3. IA carry-over — Antes de sobrescribir, copia las explicaciones de IA del scan anterior para los CVEs que siguen presentes. Así el enrich solo tiene que procesar las genuinamente nuevas.

4. Enrich con IA — Usa Claude CLI para generar explicaciones en español: qué es, por qué es grave, y cómo arreglarlo. Solo para CVEs nuevos que no tenían explicación.

5. Dependencias + Exposición + Clasificación — Conecta a cada contenedor para obtener las dependencias reales de cada paquete. Cruza con la lista de servicios expuestos a internet. Clasifica los conflictos por tipo de riesgo.

6. Dashboard — El HTML lee los JSON y muestra todo organizado. No necesita build, server, ni base de datos. Es un fichero estático que se sirve con nginx.

🧭 Cómo navegar el dashboard

El dashboard tiene 4 zonas principales, de arriba a abajo:

1. Tarjetas de resumen (arriba)

4 tarjetas con los totales: Críticos, Altos, Medios, Total. Son clickeables — hacen click para filtrar por esa severidad. El gráfico se sincroniza automáticamente.

2. Gráfico de tendencias (colapsable)

Muestra la evolución de vulnerabilidades a lo largo del tiempo. Click en una línea o en la leyenda filtra por esa severidad. Hover resalta la línea estilo Grafana. Se colapsa automáticamente cuando usas las pestañas.

3. Pestañas (centro)

5 vistas independientes: Máquinas, Actuar, Monitorizar, Conflictos, Resueltas. Los filtros de las pestañas son independientes de los filtros de las tarjetas/gráfico.

4. Lista de vulnerabilidades (abajo)

Aparece cuando filtras por severidad (tarjetas/gráfico) o cuando entras en una pestaña. Tiene buscador, chips de severidad, e infinite scroll (carga de 50 en 50 al bajar).

Memoria — La URL guarda tu posición: pestaña, máquina, filtro de severidad, CVE abierto, y estado del gráfico. Al refrescar la página, vuelves exactamente donde estabas.

📑 Pestañas

Máquinas

Vista de los servidores de tu fleet. Cada tarjeta muestra cuántas vulnerabilidades tiene por severidad. Las máquinas en gris no se pudieron escanear. Al hacer click en una máquina, ves solo sus vulnerabilidades con chips de severidad para filtrar.

Actuar

Vulnerabilidades que tienen solución disponible. Trivy detectó una versión del paquete que corrige el problema. Estas son las que hay que priorizar — especialmente las marcadas con 🌐 (expuestas a internet).

Monitorizar

Vulnerabilidades que NO tienen solución disponible. El proveedor del paquete aún no ha publicado un parche. No puedes hacer nada excepto esperar y vigilar que se publique una actualización.

Conflictos

Vulnerabilidades que tienen solución PERO actualizarlas puede causar problemas. Son las más delicadas. Cada conflicto tiene su tipo y nivel de riesgo (ver sección Tipos de conflicto).

Resueltas

Vulnerabilidades que ya no aparecen en el último escaneo. Se arreglaron, la imagen se actualizó, o el contenedor fue eliminado. Muestran un badge verde con la fecha de resolución.

🔎 Panel de detalle (8 secciones)

Al hacer click en cualquier vulnerabilidad se despliega su detalle completo con 8 secciones:

1. ¿Qué es esta vulnerabilidad?

Explicación en español sencillo generada por IA. Describe qué hace la vulnerabilidad, cómo funciona el ataque, y qué permite al atacante. Sin jerga técnica.

2. ¿Por qué es crítico/alto/medio?

Explicación del impacto real en tu infraestructura específica. Menciona las máquinas afectadas y el riesgo concreto para el negocio.

3. Paquete afectado

Nombre del paquete, si viene de una imagen Docker o del sistema operativo, versión actual instalada (en rojo), y versión corregida (en verde). Si no hay versión corregida, dice "Sin solución aún".

4. ¿Dónde afecta?

Lista de máquinas con las imágenes Docker que contienen el paquete vulnerable. Cada imagen muestra el servicio del docker-compose entre paréntesis. Al pasar el ratón muestra la ruta del compose en el servidor.

Si la vulnerabilidad está expuesta a internet, aparece un banner rojo: 🌐 Expuesto a internet via api.example.com

5. Paquetes dependientes

Lista de paquetes reales que dependen del paquete vulnerable, obtenidos directamente de cada contenedor con dpkg-query (Debian) o apk info --rdepends (Alpine). Si actualizas el paquete, estos otros paquetes pueden verse afectados.

6. Conflicto de actualización

Solo aparece si hay conflicto. Muestra dos badges (tipo + riesgo) y 4 campos: Problema, Situación actual, Qué pasa si actualizas, y Recomendación. Ver sección Tipos de conflicto para más detalle.

7. ¿Qué hacer?

Pasos exactos para arreglar. Tres colores:

Verde — Seguro de actualizar

Naranja — Actualizar con cuidado (conflicto)

Gris — Sin solución disponible

8. Enlace NVD

Link a la Base de Datos Nacional de Vulnerabilidades de EEUU (NVD) donde está toda la información técnica oficial del CVE: vector de ataque, score CVSS, referencias, y parches.

🚨 Severidades

SeveridadSignificadoAcción
CRÍTICO Permite ejecución de código remoto, robo de datos, o control total del servidor. Un atacante puede explotarlo desde internet sin credenciales. Arreglar inmediatamente. Si está expuesto a internet (🌐), es emergencia.
ALTO Permite ataques significativos pero con condiciones específicas: necesita acceso previo, interacción del usuario, o una configuración particular. Arreglar esta semana. Priorizar los expuestos a internet.
MEDIO Impacto limitado o requiere acceso local previo. Difícil de explotar remotamente. Arreglar cuando sea posible. No es urgente.
BAJO Impacto mínimo. Generalmente requiere acceso físico o condiciones muy específicas. Planificar para próximo ciclo de mantenimiento.

⚠️ Tipos de conflicto

No todos los conflictos son iguales. Algunos son seguros de actualizar y otros pueden romper la aplicación. El dashboard clasifica cada conflicto por tipo y nivel de riesgo:

🟢 No toca código, no rompe nada — solo rebuild Docker

Estos paquetes son infraestructura pura. Actualizarlos no afecta al código de tu aplicación. Solo hay que reconstruir la imagen Docker.

TLS/Cifrado

Paquetes: libssl3, libcrypto3, openssl, libssl-dev

Qué son: Librerías de cifrado que manejan HTTPS y conexiones seguras.

¿Afecta al código? No. Las actualizaciones de seguridad de OpenSSL son retrocompatibles.

¿Afecta a la infraestructura? No. El servicio sigue funcionando igual después del rebuild.

Cómo actualizar: docker compose build --no-cache && docker compose up -d

Librería de imagen

Paquetes: curl, libcurl, libxml2, zlib, libexpat

Qué son: Librerías del sistema que vienen preinstaladas en la imagen Docker base.

¿Afecta al código? No. Son librerías internas que la app no importa directamente.

¿Afecta a la infraestructura? No. Son actualizaciones de seguridad sin cambios de funcionalidad.

Cómo actualizar: docker compose build --no-cache && docker compose up -d o apk upgrade / apt upgrade

🟡 Puede romper el código de la aplicación — probar en staging primero

Estos paquetes están conectados directamente con tu código. Si cambian su API o comportamiento, partes de la aplicación pueden dejar de funcionar.

Dependencia de app

Paquetes: python3-pyasn1, python3-urllib3, jspdf, xgrammar

Qué son: Librerías que tu código importa directamente con import o require().

¿Afecta al código? Sí. Si cambian una función que el código usa, la app se rompe. Ejemplo: si urllib3 cambia cómo maneja los timeouts, the HTTP calls of the app pueden fallar.

¿Afecta a la infraestructura? No directamente, pero la app puede dejar de funcionar.

Cómo actualizar: Cambiar la versión en requirements.txt o package.json → ejecutar tests → desplegar en staging → esperar 24h → si ok, pasar a prod.

Runtime

Paquetes: stdlib (Go), libpython3.9, libpython3.11

Qué son: El motor sobre el que se ejecuta todo el código. Go stdlib es el runtime de Go, libpython es el de Python.

¿Afecta al código? Puede. Una actualización del runtime puede cambiar el comportamiento de funciones estándar que el código usa. Es raro, pero cuando pasa es difícil de detectar.

¿Afecta a la infraestructura? No directamente, pero todos los servicios escritos en ese lenguaje se ven afectados.

Cómo actualizar: Cambiar la versión del runtime en el Dockerfile → recompilar todos los binarios → desplegar en staging → probar exhaustivamente → si ok, pasar a prod.

🔴 Puede romper todo el contenedor — solo con rebuild completo de imagen base

Estos son los cimientos del sistema. Actualizarlos de forma aislada es como cambiar los cimientos de una casa sin tocar las paredes — todo se puede caer.

Sistema base

Paquetes: libc-bin, libc6, libc6-compat, linux-libc-dev

Qué son: Las librerías fundamentales del sistema operativo. Absolutamente TODO dentro del contenedor depende de ellas — desde bash hasta Python, desde curl hasta nginx.

¿Afecta al código? No directamente.

¿Afecta a la infraestructura? Sí, gravemente. Actualizar solo libc6 sin actualizar el resto puede dejar el contenedor completamente inservible. Otros programas compilados contra la versión anterior pueden crashear.

Cómo actualizar: Actualizar la imagen base entera en el Dockerfile (ej: FROM debian:11 → FROM debian:12) → rebuild completo → probar todo en staging → solo entonces pasar a prod.

Lo que NUNCA hay que hacer: apt upgrade libc6 manualmente dentro de un contenedor en producción.

Regla de oro: Siempre probar en staging antes de aplicar en producción. Incluso las actualizaciones de "riesgo bajo" pueden tener efectos inesperados en configuraciones específicas.

🌐 Exposición a internet

Las vulnerabilidades marcadas con 🌐 están en contenedores que son accesibles desde internet a través de nginx reverse proxy. Son las más urgentes porque cualquier persona en el mundo puede intentar explotarlas.

Servicios NO expuestos (solo red interna)

Redis (6379), PostgreSQL (5431/5432), Qdrant (6333), Grafana, Prometheus, y los exporters solo son accesibles vía Tailscale VPN o red privada de AWS. Los security groups bloquean el acceso externo.

Prioridad absoluta: Una vulnerabilidad CRÍTICA + 🌐 es una emergencia. Significa que un atacante puede explotar esa vulnerabilidad directamente desde internet.

🔗 Dependencias reales

La sección "Paquetes dependientes" de cada vulnerabilidad muestra datos reales obtenidos directamente de cada contenedor — no estimaciones ni heurísticas.

¿Cómo se obtienen?

El script trivy-deps.py conecta por SSH a cada máquina, ejecuta docker exec en cada contenedor, y pregunta al package manager qué paquetes dependen del paquete vulnerable:

Debian/Ubuntu: dpkg-query → build_reverse_deps() Alpine: apk info --rdepends [paquete]

¿Qué significan?

Si libssl3 tiene dependientes [openssl, libcurl, libkrb5-3], significa que si actualizas libssl3, esos otros paquetes también pueden verse afectados. No significa que van a romperse — solo que dependen de él y hay que tenerlo en cuenta.

¿Por qué algunas no tienen dependencias?

Los paquetes "leaf" (hojas) como jspdf, xgrammar o paquetes npm no tienen otros paquetes que dependan de ellos dentro del contenedor. Son el final de la cadena de dependencias. Son los más seguros de actualizar.

🤖 Análisis con IA

Cada vulnerabilidad tiene 3 campos generados por un LLM:

CampoQué contiene
¿Qué es?Explicación sencilla de la vulnerabilidad: qué hace, cómo funciona el ataque, qué permite al atacante.
¿Por qué es grave?Impacto real en tu infraestructura: qué máquinas afecta, qué servicios están en riesgo, qué puede pasar.
¿Qué hacer?Pasos exactos: comandos, ficheros, servicios a reiniciar. Adaptado al entorno específico (Alpine/Debian/Docker).

La IA procesa las vulnerabilidades en batches de 10, con reintentos automáticos y guardado incremental. Si el proceso se interrumpe, el progreso nunca se pierde.

Para las vulnerabilidades resueltas, la IA también se copia para que la pestaña "Resueltas" tenga la misma información.

🖥️ Tu fleet

El dashboard se autoconfigura desde reports/latest.json. Cada máquina escaneada aparece con un color asignado automáticamente y el rol que definas en tu inventory.json. No hay máquinas hardcoded — añade o quita servidores y el dashboard se adapta tras el siguiente scan.

Para personalizar el color y rol de una máquina, edita MACHINE_DEFAULTS en dashboard/index.html con tu propio mapeo:

const MACHINE_DEFAULTS = { "tu-host-1": { role: "Producción", color: "#dc2645", icon: "🔴" }, "tu-host-2": { role: "Staging", color: "#e05520", icon: "🟠" }, };

🎯 Cómo actuar ante una vulnerabilidad

Paso 1: Evaluar la prioridad

CondiciónPrioridadPlazo
Crítico + 🌐 Expuesto + En producciónEMERGENCIAHoy
Crítico + 🌐 ExpuestoMUY ALTA24h
Crítico sin exposiciónALTAEsta semana
Alto + 🌐 ExpuestoALTAEsta semana
Alto sin exposiciónMEDIA2 semanas
MedioBAJAPróximo ciclo

Paso 2: Revisar el tipo de conflicto

Si la vulnerabilidad está en la pestaña Conflictos, revisa el tipo antes de actuar:

🟢 Librería de imagen o TLS/Cifrado → No toca código ni infraestructura. Rebuild de imagen Docker y listo.

🟡 Runtime o Dependencia de app → Puede romper el código de la app. Actualizar en staging, probar, esperar 24h, solo entonces prod.

🔴 Sistema base → Puede romper todo el contenedor. Solo con rebuild completo de la imagen base (cambiar FROM en Dockerfile).

Paso 3: Aplicar la actualización

Sigue los pasos de la sección "¿Qué hacer?" de la vulnerabilidad. Siempre:

1. Aplicar en staging primero 2. Verificar que los servicios funcionan 3. Esperar 24h monitorizando 4. Aplicar en producción 5. Verificar de nuevo

Paso 4: Verificar en el próximo scan

El domingo siguiente el scan detectará que la vulnerabilidad desapareció y la moverá a la pestaña "Resueltas" con badge verde.

🔄 Automatización y cron

Sugerencia: corre el scan semanalmente vía cron en el host con acceso SSH a tu fleet:

crontab -e 0 1 * * 0 /opt/socials-trivy/scripts/trivy-scan.sh >> /tmp/trivy-scan.log 2>&1

¿Qué ejecuta?

➕ Añadir una máquina nueva

Para añadir una nueva máquina al escaneo:

1. Añadir la máquina a inventory.json: {"name": "nueva-maquina", "role": "descripción", "ssh": "ssh user@ip"} 2. (Opcional) Personalizar color y rol en MACHINE_DEFAULTS de dashboard/index.html: "nueva-maquina": { role: "Descripción", color: "#hexcolor", icon: "🔵" } 3. Si tiene servicios expuestos, añadir a exposed.json 4. El próximo scan la incluirá automáticamente — si no la añades a MACHINE_DEFAULTS, el dashboard le asigna un color automáticamente.
